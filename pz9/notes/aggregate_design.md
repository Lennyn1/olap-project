## Виджет для З10

Линейный график **«Выручка по дням и магазинам»**: ось X — `sale_date`, серия — `store_id` (при желании имя магазина через JOIN с `dim_store`), показатель — `SUM(amount_sum)`.

**Зерно сводки:** одна строка `retail_pz7.agg_daily_store_sales` = **один календарный день × один магазин**. Это НЕ зерно `fact_sales`: в факте одна строка — одна запись о продаже определённого товара в магазине на дату.

- `amount_sum`: `SUM(fact_sales.amount)` по дню и магазину, `Decimal(18,2)`.
- `qty_sum`: `SUM(fact_sales.qty)` по дню и магазину.
- `sales_rows`: количество детальных строк, вошедших в группу.

## Эталон метрики

Главная метрика по-прежнему вычисляется **только из детальной** `retail_pz7.fact_sales`: `SELECT sum(amount) AS total_revenue FROM retail_pz7.fact_sales;`. Агрегат предназначен для быстрого отображения графика и не заменяет канонический SQL из З04.

## Обновление после З07

Это **обычная агрегатная таблица MergeTree**, а НЕ автоматически обновляемая materialized view. После каждого повторного запуска `pz7/etl/load_clickhouse.py`, пересоздающего `retail_pz7`, нужно заново выполнить `py -3.11 pz9/scripts/build_aggregate.py`. Скрипт создаёт сводку, очищает **только её** через `TRUNCATE` и снова заполняет `INSERT ... SELECT`. Он не очищает и не изменяет `fact_sales`.

Поскольку refresh — два отдельных SQL-запроса, в промежутке таблица агрегата может быть пустой, а при сбое после `TRUNCATE` останется пустой или неполной. Для учебного стенда допустимо; в промышленном контуре потребуется атомарная замена подготовленной таблицы.
