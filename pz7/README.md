## Отдельная база и стратегия повтора

Все операции P07 выполняются в самостоятельной базе **`retail_pz7`**, не затрагивая учебную базу `retail_dw`, поднятую в З01. Скрипт сначала проверяет доступность CSV и эталонной DuckDB. Затем каждый раз **удаляет только базу `retail_pz7` и создаёт её заново**, загружая сперва справочники, затем `fact_sales`. Это учебный `full refresh`: повторная загрузка не удваивает продажи. **Ограничение:** если ошибка возникает после удаления базы, `retail_pz7` может остаться неполной; после исправления ошибки повторите команду. Для production необходима схема staging + атомарная публикация.

## Почему `ORDER BY (date_id, store_id, product_id)`?

Частые вопросы из паспорта анализируют продажи по времени и магазинам, поэтому первыми в сортировочном ключе факта поставлены `date_id` и `store_id`. `product_id` в конце помогает сгруппировать записи конкретных товаров внутри диапазона времени и магазина. На учебных 15 строках заметного выигрыша в скорости ждать не нужно. **`ORDER BY` в `MergeTree` определяет физический порядок и разреженный индекс, но НЕ гарантирует уникальность** (`sale_id` можно ошибочно загрузить дважды).

Измерения упорядочены по натуральным идентификаторам, поскольку соединяются с фактом по ним. Партиционирование на этом этапе необязательно по чеклисту P07.

## Меры, зерно и сверка

**Grain:** одна строка `fact_sales` — одна зарегистрированная позиция продажи конкретного товара в конкретном магазине на определённую дату. `sale_id` идентифицирует строку.

Денежная мера `amount` хранится как `Decimal(12,2)`, не как `Float`. Контрольное значение исходных 15 записей: `SUM(amount) = 264.00` условных денежных единиц.

Эталон для DuckDB — `pz4/sql/canonical_metric.sql`:

```sql
SELECT SUM(amount) AS total_revenue
FROM fact_sales;
```

Аналогичный запрос для ClickHouse:

```sql
SELECT SUM(amount) AS total_revenue
FROM retail_pz7.fact_sales;
```

Одинаковые условия: без фильтров, одни и те же исходные данные. Скрипт сверяет `count(*)` каждого измерения и факта, `sum(amount)`, отсутствие повторяющихся `sale_id` и «сирот» FK.

## Команды ручной проверки

```powershell
docker exec olap_clickhouse clickhouse-client --query "SHOW TABLES FROM retail_pz7"
docker exec olap_clickhouse clickhouse-client --query "SELECT count(), sum(amount) FROM retail_pz7.fact_sales"
docker exec olap_clickhouse clickhouse-client --query "SHOW CREATE TABLE retail_pz7.fact_sales"
```

Ожидается `15` и `264.00` (ClickHouse может отобразить `264`). В ClickHouse `ORDER BY` — не уникальный PK.
